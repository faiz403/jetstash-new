## Findings

**Identity thresholds (provisional 5 km / 50% name words) — unchanged.**
- Across 39 agreeing airports the Google point was at most 1.68 km (mean 0.56 km) from the catalogue point. 5 km was never approached: there is room to tighten, but no evidence yet that it is needed. No airport was more than 5 km off.
- False negatives: **MAN** (Google types Manchester Airport as `bus_station`/`transit_station`; name matches; 1.87 km) and **LYR** (see catalogue issues). The type rule is right to fail closed; both are NEEDS_REVIEW, not accepted.
- Localised names: **TIJ** matched only on the IATA code (0% name words) and **SYD** on IATA (33%); LHR, LUX and IAD sat exactly on the 50% line. The IATA-in-address escape hatch is doing real work; the name rule alone would have failed renamed or non-English airports.
- **BEK** (Bareilly): Google returns only the city, no airport POI, so FAIL is correct. Kept catalogued, no capability.

**Catalogue issues.** LYR is `NO` in OurAirports but Google places Svalbard Airport in `SJ` (a territory code); one unrestricted lookup surfaces this as `catalogue_data`. Expect the same for other territories (PR, GU, GL, FO ...). IKO passes (0.1 km): the old name-based exclusion was wrong.

**Google coverage / road routing.** No airport failed for lack of a DRIVE route. Island and remote airports all routed (MLE 17 min, HNL 38, KEF 26, ASP 22, IKO 1). The sample contained no airport with genuinely no road, so that class is untested. Coverage was uniform across UK, Europe, North and South America, Middle East, South Asia, East/SE Asia, Oceania and Africa.

**Destination-resolution engine (shared, not airport-specific) — the real blockers.** Three airports failed on the *probe destination* only, and re-testing showed it is systematic:
- Brazil: "Campinas"/"Santos" → `TOO_BROAD_TYPE` (Brazilian cities are `administrative_area_level_2`); "Sao Jose dos Campos"/"Sao Paulo" → `PRIMARY_PLACE_MISMATCH` (input without diacritics vs "São"). Every GRU destination tried failed, including a street address.
- Singapore: "Jurong East", "Orchard Road", "1 Orchard Road" and "Singapore" were all refused (`PRIMARY_PLACE_MISMATCH` / `TOO_BROAD_TYPE`); a city-state has no locality component.
- Iceland: "Reykjavik" → `PRIMARY_PLACE_MISMATCH` against "Reykjavík" (diacritics). KEF passed on a fallback ("Grindavik").

These fail closed (no wrong journey was ever shown), but a traveller landing at GRU or SIN could not currently get an answer. GRU and SIN are therefore `route_testable`, not `road_supported`. Not changed in this phase: fixing the shared resolver (diacritic folding; locality equivalents for admin-level-2 countries and city-states) is a Phase D prerequisite and must be regression-tested against Pakistan and Manchester.

**Cross-border policy (GVA, BSL, LUX, plus TIJ, SIN, HKG).** The configured policies behaved exactly as configured on all 13 policy checks: GVA→Annecy (FR) routes, →Milan refused; BSL→Mulhouse (FR) and Freiburg (DE) route, →Milan refused; LUX→Thionville (FR), Trier (DE) and Arlon (BE) route, →Amsterdam refused; SIN→Johor Bahru, HKG→Shenzhen and TIJ→San Diego refused under SAME_COUNTRY. Google can route across all of these borders; policies were **not** widened because of that. Open product question: TIJ→San Diego and SIN→Johor Bahru are legitimate real-world trips that are currently refused.

**Timezone.** The catalogue zones for the 42 airports are all plausible (YLL America/Edmonton, ASP Australia/Darwin, IKO America/Adak, LYR Arctic/Longyearbyen, half-hour Asia/Kolkata). **Not independently verified:** Google's Time Zone API is not enabled on the key used, so every record is `NOT_CHECKED` and the zones rest on offline tz-lookup only. Enabling that API (one console action) lets the probe cross-check; it already supports it.

**Generic UI (internal QA: dev-only switch, headless Edge, desktop and 390 px mobile, no horizontal overflow).** Verified: landing time, exit buffer, pickup wait, destination, optional deadline / reason / readiness; "Airport-level estimate" badge and per-result line; focus moves to the answer; wrong-country refusal (Paris from LHR); venue confirmation ("Legoland Windsor Resort" → Yes → route); multi-venue selection ("Premier Inn Slough" → 3 candidates → pick → route). Two defects found and fixed: focus could miss the answer after an async result (now an effect), and the wrong-country headline told users to "add a larger town" (now says the destination is outside the supported area). MAN still renders its own transit-first page; BEK and GRU still show "can't calculate yet".

## Recommended Phase D public-rollout rule

Release airports one at a time, as a small named cohort that grows — never "everything with evidence". An airport gets an entry in `ARRIVE_BY_RELEASED_AIRPORTS` (dated, with an approval note) only when: (1) `road_supported` evidence exists and has been re-probed recently; (2) the shared destination-resolution fixes above are in and regression-tested for that airport's country; (3) its destination policy has been explicitly decided against how travellers really use it; (4) the user-facing data-attribution notice is live; (5) the rate-limiter decision has been made for the expected traffic.
